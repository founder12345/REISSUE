# Security and launch readiness

- Passwords use scrypt with unique salts. Session secrets are hashed in PostgreSQL and carried in HTTP-only SameSite cookies with Secure enabled on HTTPS deployments. Write routes require the configured origin, and account and brand authorisation is checked server-side.
- Parameterised values and allowlisted SQL identifiers protect the database. React escapes user text. Browser security headers restrict framing and basic resource handling. Image uploads require a moderator, are size and pixel bounded, validate decoded formats and are re-encoded as still WebP to strip metadata. Keep the object store private.
- Account deletion removes sessions, saved products, preferences, search history, notifications, collections and memberships. Public campaign records and comments can remain with the account reference cleared. Application logs should exclude sensitive request bodies and cookie headers.
- Search analytics default to off. Enabled events omit user identifiers and skip obvious email, URL and long-number queries. This heuristic cannot detect all personal data. Establish a retention period and review edge/hosting logs before enabling analytics. Set database maintenance to expire old sessions and rate-limit rows, and to delete aged search events and validated import data in line with the privacy policy.
- New brands and categories are created by moderators. Brand membership is assigned after human evidence review. Evidence quality depends on the operating team. For a public launch, add account email verification and password recovery, administrator MFA, member revocation workflows, abuse escalation and a formal brand verification policy.
- Existing rate limits protect mutation and password routes. Deploy a trusted edge limiter for unauthenticated search, account creation and authenticated abuse across multiple accounts. An email-and-password account alone does not prove unique human identity.
- Production readiness depends on a sourced catalogue and rights-cleared imagery. Demo fixtures and hero artwork are illustrative. Product availability is unknown unless evidence is supplied, and verification is a separate moderation decision.
- Brand dashboard reporting includes active and historical recorded interest, a monthly count, preference distributions and summary CSV. It does not store historical point-in-time snapshots. Search conversion events are directional counts from application links, not attributed funnels. Automated trend alerts and large-catalogue load targets remain follow-up work.
- Community updates are in-app. Email delivery, direct messaging and payments are outside this implementation. Collections use archived product visuals rather than custom cover uploads. Brand revival announcements use official campaign updates. Public launch requires a privacy and consumer protection review, accessibility review and operational monitoring.
- S3-compatible upload and serving require a configured bucket. Exercise them against the actual provider before enabling them in a public environment. Keep a process for orphan-object cleanup and image takedowns. A cached public thumbnail can persist after a record becomes hidden.
